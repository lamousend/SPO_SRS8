# Резервная копия и восстановление данных (учебная среда)

Сценарий `scripts/backup_restore.py` нужен, чтобы не потерять данные при пересоздании базы, проверить,
что копия действительно восстанавливается, и перенести данные между SQLite и PostgreSQL.
База выбирается как обычно: задана `DATABASE_URL` — PostgreSQL, не задана — локальная `db.sqlite3`.

| Команда | Что делает |
|---------|------------|
| `backup [файл.json]` | снимает копию (по умолчанию `backups/data-ГГГГММДД-ЧЧММСС.json`) |
| `verify файл.json` | создаёт **временную пустую** базу, выполняет `migrate`, загружает копию и проверяет её; рабочая база не затрагивается |
| `restore файл.json` | загружает копию в **пустую** базу после `migrate` и сразу проверяет результат; в непустую базу — только с `--force` |
| `check [файл.json]` | проверяет текущую базу: число записей по моделям (и совпадение с копией, если указана) и бизнес-инварианты |

Проверяемые инварианты (нарушение — код возврата 1):

- для каждого оборудования `available_q + сумма quantity выданных бронирований = total_q`;
- у каждого бронирования есть событие создания; у выданного и возвращённого — событие выдачи, у возвращённого — возврата;
- удалённым может быть только бронирование в состоянии `created`.

## Что попадает в копию

Пользователи (**с хэшами паролей**), группы, справочники, заявки, бронирования, история и журнал активности.
Исключены служебные таблицы (`contenttypes`, `auth.permission`, `sessions`, `admin.logentry`) — они создаются `migrate`.
Каталог `backups/` внесён в `.gitignore`: файл копии — чувствительные данные, его нельзя публиковать и прикладывать к отчёту.

## Сценарий 1. Регулярная копия и её проверка

```bash
python scripts/backup_restore.py backup backups/demo.json
# Копия сохранена: backups/demo.json (объектов: 22)
python scripts/backup_restore.py verify backups/demo.json
# ... accounts.equipment  в копии 3  в базе 3  OK ...
# остатки и история согласованы
# ПРОВЕРКА ПРОЙДЕНА
```

Копию, которая не прошла `verify`, считать непригодной и снять заново.

## Сценарий 2. Восстановление после потери базы

1. Создать пустую базу: удалить испорченный `db.sqlite3` (или создать новую PostgreSQL) и выполнить `python manage.py migrate`.
2. `python scripts/backup_restore.py restore backups/demo.json` — загрузка и автоматическая проверка.
3. Войти под прежним пользователем, открыть `/reservations/`: бронирования, остатки и история на месте.

## Сценарий 3. Перенос SQLite → PostgreSQL (например, на Render)

```bash
python scripts/backup_restore.py backup backups/transfer.json        # без DATABASE_URL: из SQLite
export DATABASE_URL='<External Database URL>'                      # Windows: $env:DATABASE_URL = "..."
python manage.py migrate
python scripts/backup_restore.py restore backups/transfer.json       # загрузка и проверка в PostgreSQL
```

После переноса последовательности `id` в PostgreSQL продолжаются (это делает `loaddata`), новые записи создаются без конфликтов,
пароли пользователей прежние. Обратный перенос — те же шаги в обратном порядке. Значение `DATABASE_URL` не записывается в файлы.

## Защита от ошибок

| Ситуация | Поведение |
|----------|-----------|
| `restore` в базу, где уже есть данные | отказ с перечнем непустых таблиц, код 1; `--force` — загрузить поверх (возможны конфликты ключей) |
| в базе нет таблиц | сообщение «сначала выполните migrate», код 1 |
| копия испорчена (например, вручную изменён остаток) | `verify` / `restore` выводят нарушение инварианта и `ПРОВЕРКА НЕ ПРОЙДЕНА`, код 1 |

## Проверка сценария

Выполнено в учебной среде: копия рабочей SQLite (22 объекта: 3 пользователя, 3 категории, 3 вида оборудования,
3 бронирования, 7 событий, 3 записи журнала) проверена `verify`, затем восстановлена в новую PostgreSQL 16 — число записей
совпало, инварианты выполнены, новая запись получила следующий `id`, пользователь `student1` входит с прежним паролем.
Повторный `restore` в ту же базу отклонён; копия с вручную испорченным остатком отклонена `verify`.
В CI сценарии 1 и 3 выполняются на каждый `push` ([ci-and-releases.md](ci-and-releases.md)).
