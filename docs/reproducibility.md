# Проверка воспроизводимости

Цель — убедиться, что другой человек запускает проект **только по документации**. Проверка выполняется на новой
копии репозитория и в новом виртуальном окружении; все шаги, которых не хватало в инструкции, добавляются в
документацию, после чего проверка повторяется.

## Автоматический сценарий

```bash
bash scripts/verify_clean_start.sh
```

Скрипт выполняет инструкцию [local-setup.md](local-setup.md) в одноразовом каталоге:

| Шаг | Что делается | Что доказывает |
|-----|--------------|----------------|
| 1 | копируются **только файлы репозитория** (`git ls-files`, без `.git` — по правилам `.gitignore`) | проекту не нужны локальные `.env`, `db.sqlite3` и незакоммиченные файлы |
| 2 | новый venv, `pip install -r requirements.txt` (`--skip-install` — пропустить) | зависимостей достаточно |
| 3 | переменные `DJANGO_*`/`DATABASE_URL` оболочки очищаются; `python scripts/make_env.py` (копия `.env.example` с новым ключом); `check` | конфигурация собирается по образцу |
| 4 | `migrate`, `showmigrations` без `[ ]` | схема создаётся в пустой базе |
| 5–6 | `seed_lab_data`, 21 автотест | тестовые данные и бизнес-правила |
| 7–8 | `runserver`, `/healthz/`, страница входа; вход, заявка (POST, PATCH), бронирование (POST, выдача) | UI и API работают |
| 9 | перезапуск сервера; заявка, выданное бронирование, уменьшенный остаток и история найдены | данные сохраняются |
| 10 | `DJANGO_DEBUG=false`, `collectstatic`, Gunicorn: `/healthz/` 200, CSS 200, чужой Host 400, 404 | production-конфигурация из [deployment.md](deployment.md) |

В конце печатается таблица шагов; код возврата 0 — все шаги успешны. Тот же сценарий на пустой PostgreSQL:
`VERIFY_DATABASE_URL=postgresql://USER:PASSWORD@localhost:5432/verify bash scripts/verify_clean_start.sh`.
В CI сценарий выполняется на каждый `push` для SQLite и для PostgreSQL 16 ([ci-and-releases.md](ci-and-releases.md)).

## Контрольные проверки

Первая проверка выполнена по шагам [local-setup.md](local-setup.md) на чистой копии проекта (Linux, Python 3.13.18).
Колонка «Подтверждение» — что именно доказывает результат.

| № | Контрольная проверка | Команда / действие | Фактический результат | Подтверждение |
|---|----------------------|--------------------|-----------------------|---------------|
| 1 | Зависимости устанавливаются по требованиям | `python -m pip install -r requirements.txt` | **Не подтверждено в среде проверки**: доступ к PyPI был закрыт политикой сети. Пакеты тех же версий (Django 6.1.1, DRF 3.18.3, WhiteNoise 6.12.0, dj-database-url 3.1.2, asgiref 3.12.1, sqlparse 0.6.0, Gunicorn 26.2.0) подключены из исходников GitHub по тегам; проект с ними запустился | Требуется выполнить на своём компьютере и приложить вывод `pip install` (см. форму ниже) |
| 2 | Конфигурация собирается по `.env.example` | `cp .env.example .env`, `python manage.py check` | Без `.env`: `ImproperlyConfigured: Set DJANGO_SECRET_KEY`. С `.env`: `System check identified no issues (0 silenced).` Секреты из исходного кода не нужны | Вывод двух запусков `check` |
| 3 | Миграции выполняются | `python manage.py migrate` | Применены `accounts.0001`…`0007`, `dashboards.0001`, `sessions.0001` — все `OK` | Вывод `migrate`; `showmigrations` |
| 4 | Интерфейс доступен и оформлен | `runserver`, вход как `student1`, `/reservations/` | страница с формой, таблицей остатков и списком в стиле Tabler; `GET /accounts/login/` → 200 | Скриншот страницы |
| 5 | GET и изменяющая операция API работают | UI: создание бронирования; `scripts/smoke_api.py` | `GET /api/equipment/` → 200; `GET /api/reservations/` → 200; `POST /api/reservations/` → 201 | Журнал запросов браузера без секретов |
| 6 | Данные сохраняются после перезапуска | остановить сервер, запустить, `GET /api/tickets/` | заявка «Проверка чистого запуска», созданная до перезапуска, найдена | Повторное чтение ранее созданного объекта |
| 7 | Типовая ошибка распознаётся по инструкции | запуск без `.env` | симптом `ImproperlyConfigured: Set DJANGO_SECRET_KEY` описан в [troubleshooting.md](troubleshooting.md), п. 1; исправление — `cp .env.example .env` | Описание симптома, диагностики, исправления |

Дополнительно проверено: `python manage.py test accounts` — 21 тест, `OK` (на SQLite и PostgreSQL 16); `collectstatic` — 2065 файлов;
Gunicorn при `DJANGO_DEBUG=false` отвечает на `/healthz/` (`200`), раздаёт `/static/...` (`200`), на чужой `Host`
отвечает `400`, на несуществующий адрес — `404`.

## Недостающие шаги, выявленные при проверке

| № | Что не хватало | Как проявлялось | Что исправлено |
|---|----------------|-----------------|----------------|
| 1 | Нигде не описано, как задать `DJANGO_SECRET_KEY` локально; `.env` не читался | падение `ImproperlyConfigured` на первой же команде | добавлена функция `load_dotenv` в `config/settings.py`, раздел «Конфигурация» в README и local-setup |
| 2 | `.env.example` содержал значения Render (`DEBUG=False`, хост `your-app.onrender.com`) | локальный запуск невозможен без правок | `.env.example` переписан для локальной работы, с пояснениями и вариантом для Render |
| 3 | Нет тестовых данных: категории и оборудование доступны в API только на чтение | на странице пустые списки | добавлена команда `seed_lab_data` |
| 4 | `README.md` — пустая заглушка | непонятно, что это и как запустить | написан README и комплект `docs/` |
| 5 | `requirements.txt` в UTF-16 | риск нечитаемости инструментами | пересохранён в UTF-8; проверка в `scripts/check_docs.py` |
| 6 | Не описана проверка, что всё работает | нет критерия успеха | добавлены автотесты, `verify_clean_start.sh` |

попросите одногруппника выполнить его под наблюдением. Запишите результат.
